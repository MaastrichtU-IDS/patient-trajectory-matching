# Trajectory-graph profile

**Profile:** `trajectory-graph-1.0` · **Code:** [`patterns/trajectory_graph.py`](../patterns/trajectory_graph.py), reference [`patterns/trajectory_graph_reference.py`](../patterns/trajectory_graph_reference.py) · **Tests:** `python -m patterns.test_trajectory_graph`

This profile decides whether a patient's events match a trajectory shaped as a sequence, a tree or a graph, when event times are known only within ranges. It is the engine counterpart of the [trajectory mockup](../demos/mockups/trajectory/), whose browser search it is meant to replace (see [engine design](engine-design.md) §3 and §7.5). Its semantics are the mockup's; its decision procedure avoids the mockup's exhaustive search wherever a polynomial method is sound.

## Input

The engine reads a projected execution form, not RDF. Concept matching is the caller's: each event lists every concept it counts as, ancestors included. The [SULO adapter](trajectory-graph-sulo-adapter.md) produces this form from bounded, patient-local and claim snapshots, and carries each bound step's evidence back.

The trajectory mockup is one caller. `demos/mockups/server.py` exposes `POST /api/trajectory-graph/match` with `{query, patients}`. The page resolves each step's candidates itself, including relaxed alternatives, emits them as events tagged with the step, and expresses each relaxation as `widen_concept` to the alternative's tag, `extend_max` or `extend_grace`. It sends times in minutes. A candidate emitted for several steps is one recorded event, so every copy names the same `start_var` and `end_var`, keyed by the underlying item (or measurement record) and whether it is a point or a span. The page's own network intersects the ranges of an event seen by several steps, as the engine does. On the synthetic cohort the engine and the page's own search agree for every patient (`demos/mockups/test_engine_parity.cjs`). The page offers relaxation sets the engine treats differently in two cases: a step's concept and count relaxations cannot combine (one relaxation per step), and sets of three or four relaxations within the budget are tried by the engine but not by the page's search. No template exercises either.

**Query**

| Field | Meaning |
|---|---|
| `steps` | `{id, concept, occurrence}`. An event can bind a step if it lists the concept. `occurrence` is `any` (default), `first` or `last`: the first or last start among the matching events (see [First and last](#first-and-last-d30)) |
| `relations` | `after`: start(`to`) − start(`from`) ∈ [`min`, `max`]; either bound may be absent, and either side may be the anchor `START` or `END`. `during`: start(`to`) ≥ start(`from`) and start(`to`) − end(`from`) ≤ `grace`; `from` must be a step |
| `scope` | `any`, `from_start` (every step starts at or after `START`), `within` (between `START` and `END`) or `after` (at or after `END`) |
| `relaxations` | `widen_concept` (a step's concept replaced, e.g. by its parent), `extend_max` (an `after` relation's maximum raised) or `extend_grace` (a `during` grace raised), each with a non-negative `cost` |
| `budget` | The largest total relaxation cost tried |
| `search_budget` | Steps allowed to any one bounded search (default 40,000) |

**Patient:** `{patient_id, window: {start, end} | null, events}`. Times are integers on one declared grid, such as days or microseconds.

| Event field | Meaning |
|---|---|
| `id`, `concepts` | Identifier, unique in the patient, and every concept the event counts as |
| `start` | `[earliest, latest]` |
| `end` | `[earliest, latest \| null]`, where `null` means still ongoing; absent for a point |
| `start_var` | Optional name of the start's time variable; default `<id>.s` |
| `end_var` | Optional name of the end's time variable; default `<id>.f`. A point has none: its end is its start |
| `proper` | Optional, default `false`. `true` makes the event end strictly after it starts, at least one grid step later. A point cannot be proper |

Events that name the same variable share one time. That covers one time recorded by several sources, or a dose that starts when an exposure ends. A shared variable lies in every range that names it, and every event ends at or after it starts. A record whose shared variables no time can satisfy is refused with `EMPTY_SHARED_VARIABLE`, whether the ranges naming one variable do not meet or the events' order rules out every time. A variable name that is not a non-empty string, or an `end_var` on a point, is refused with `INVALID_EVENT_VARIABLE`. Default names are names like any other: an event whose `start_var` is `m.f` starts when event `m` ends.

**Proper events (D24).** A `proper` event ends at least one grid step after it starts: its order edge is start − end ≤ −1 instead of ≤ 0. Sources such as the bounded interval profile require it (start + 1 ≤ end, in microseconds). Without sharing it only narrows the event's own ranges: its start's latest value and its end's earliest move by at most one step. With sharing it reaches other events: if Y starts when a proper X ends, Y starts strictly after X starts. So `after` from 0 to 0 between them is impossible, and `after` at least 1 holds in every timeline. A proper event naming one variable as its start and end is always refused with `EMPTY_PROPER_EVENT`, whether or not other events name that variable. A proper event whose ranges leave no time for its end to follow its start is refused with `EMPTY_PROPER_EVENT` when no other event names its variables (D25; `EMPTY_SHARED_VARIABLE` before), and with `EMPTY_SHARED_VARIABLE` when the conflict's component contains a variable two events name, even if the event's own ranges alone would already be empty. A `proper` that is not a boolean, or any `proper` on a point, is refused with `INVALID_EVENT_PROPER`. The option is per event rather than per query or profile, for three reasons:
- it describes the record, not the question, and one patient may hold records from sources with different conventions;
- a patient's network is solved once per patient, whatever the query;
- the execution store keeps it as a column.

Without `proper` the engine decides exactly as before, byte for byte.

The patient's network is solved once per patient, in time cubic in each group of linked variables. A lone exposure links only its own two variables and costs nothing. Groups that sharing builds may together cost no more than one group of 300 variables, which solves in under a second. A larger record is refused with `SHARED_VARIABLE_COMPONENT_LIMIT` before any group is solved.

Steps may share an event, and then share its times: distinctness across steps is an NP-hard feature (engine design §7.3) and is not offered.

## Semantics

Times belong to variables, not to steps. A step's start and end are the variables its event names, so one event bound to two steps has one time, and so do two events that name one variable. A patient's own record is a simple temporal network over its variables: each lies in every range that names it, and each event ends at or after it starts (a proper event at least one grid step after). A binding is **possible** when some choice of the patient's times satisfies that network and every relation and scope constraint jointly. It is **exact** when every choice the network allows satisfies every constraint.

Every choice satisfies all the constraints exactly when, for each constraint, every choice satisfies it. So exactness is the conjunction of one test per constraint: over the patient's network, the largest value of *y* − *x* is at most hi and the smallest at least lo. Those extremes are shortest-path distances in the patient's network, which depend only on the two variables, never on the binding. Two terms on one variable differ by exactly 0, so a constraint between them is certain exactly when lo ≤ 0 ≤ hi. A variable that no event links to another ranges over its own range, and the test reduces to min(*y*) − max(*x*) ≥ lo and max(*y*) − min(*x*) ≤ hi. The mockup's exact test is the same, over the events it binds. A proper event's −1 edge is part of the network: its own ranges are solved with it, and the distances within a linked group include it. Between two variables that nothing links, the joint range is still the product of their ranges, so the pairwise kernel's closed form over the tightened ranges stays exact.

**This changes exactness.** Before shared times, each step had its own copy of its event's variables, and certainty was tested over the two ranges alone. Two facts now count toward certainty that did not before:
- an exposure's own end ≥ start;
- the zero difference between two terms on one variable.

So some bindings that were possible are now exact, and some that were possible are now impossible, because one event cannot take two times. On the trajectory page, the heavy trajectory "two seizures then a febrile seizure" moves 4 of the 48 synthetic patients from possible to relaxed/exact. They had been possible only because one seizure took two times. No template's results change.

| Status | Meaning |
|---|---|
| `exact` | Some binding is exact |
| `possible` | Some binding is possible and none is exact (a stopped exact search is noted) |
| `relaxed` | No unrelaxed binding is possible; the cheapest relaxation set that admits one, with its certainty |
| `unresolved` | The unrelaxed search stopped before finding or ruling out a binding (`SEARCH_BUDGET_EXHAUSTED`), or a `first` or `last` target the patient's facts leave uncertain made it undecided (`OCCURRENCE_ORDER_UNCERTAIN`, D30); a binding found on the picked target, or any relaxed match found, is reported beside it, not as the status |
| `none` | Every search finished and nothing matched (a stopped relaxation search is noted) |
| `excluded` | The patient has no index window |

Relaxation sets are tried in order of total cost, then size, then identifier, with at most one relaxation per step or relation, up to `budget`. The first set that admits a binding is reported.

### First and last (D30)

*Changed definition, 2026-11-11 (D30).* Before D30 the profile defined `first` and `last` syntactically: the least or greatest event in the order (start range, end range, identifier), bound whatever the times allowed. The old engine conformed to that text, but the text did not agree with the profile's semantics of `exact` and `possible`, which quantify over every choice of times. `last` took the largest *earliest* start: an event known only to lie in [60, 365] lost "last" to one exactly at 69, so "the last K before day 90" was `exact` on the event at 69 though the other may fall in November. And "X during the first exposure" was `exact` on an exposure that may not be the first. D30 changed the definition (below) so that results agree with those semantics. The identifier stays `trajectory-graph-1.0`, since every caller sends it and the change is a correction, not a second semantics; the decision log (D30) records why. *Limitation:* a match through the execution store records the engine's file digest in its context, but bare `trajectory_graph.match` and the mockups' `/api/trajectory-graph/match` do not, so their outputs from before and after D30 cannot be told apart by the output alone. A new output field would have moved every recorded result digest. The trajectory page's own "last" and "Nth from last" now count back from the latest possible start too.

- **The order.** `first` picks the least event by (start range, end range, identifier); `last` the greatest by (latest start, earliest start, end range, identifier). On exact times the two orders pick the same events as before D30.
- **Certain targets.** The picked event is *certain* when every other event carrying the concept starts strictly after it (before it, for `last`) in every choice of the patient's times, or certainly at the same time (the order then breaks the tie). A certain step binds its event, as before.
- **Uncertain, safe targets.** The true first start lies in the *envelope* [least earliest start, least latest start] over the patient's ranges of the concept's events ([greatest earliest, greatest latest] for `last`); when the events are independent, every time in it is the first start in some choice of times. The step is *safe* when the concept's events name no shared variable, no relation reads the step's end (a `during` from it) unless every such event is a point, and no other step can bind one of those events (an `any` step whose concept one of them carries, or a `first` or `last` step whose possible targets include one: its picked event if that is certain, or else any event that can be its target). A safe step is decided on a point of its own over the envelope, linked to nothing; the binding names the picked event. `exact`, `possible` and `none` are then sound: "the first K after day 90" is `none` when some K is certainly at day 69, and "the first K before day 90" is `exact`.
- **Uncertain, unsafe targets.** A binding found on the picked event proves nothing either way: the result is `unresolved` with reason `OCCURRENCE_ORDER_UNCERTAIN`, the steps in `uncertain_steps` and the binding beside it in `unverified_match` (`certainty`, `binding`, `method`). If none is found, the search is repeated with every event that can be first (last) in some choice of times, tested pair by pair, as the step's candidates: a superset of the true targets, so a `none` there is sound and stands; anything else leaves the set undecided. An undecided unrelaxed query is treated as a stopped search: the relaxation sets are tried and a relaxed match is reported beside the unresolved status. An undecided relaxation set is passed over, and the result carries `complete: false` and note `CHEAPER_RELAXATION_ORDER_UNCERTAIN` (relaxed) or `RELAXATION_ORDER_UNCERTAIN` (none). When a set was passed over for its order and another set's search stopped at its budget, the note names the budget (`CHEAPER_RELAXATION_SEARCH_STOPPED` or `RELAXATION_SEARCH_STOPPED`); `complete: false` covers both. A `none` with `RELAXATION_ORDER_UNCERTAIN` may hide a relaxed match: callers that count statuses should count it apart, as the store's reports and the store query page do.
- **Coupled targets: one envelope search (D31).** An unsafe step is *covered* when its concept's events name no variable another event names and no relation reads its end unless every such event is a point. When every unsafe step of a relaxation set is covered, the two searches above are replaced by one search in two phases; otherwise they stand.
  - *Exact phase.* Each covered step is a point of its own over its envelope, as a safe step is. An exact binding is reported `exact` (the binding names the picked event). Its absence proves nothing.
  - *Possible phase.* Each covered step's candidates are its *split*, and the phase adds *order facts*. No binding: `none`. A binding: undecided, reported as above (`unresolved` with the binding beside it, certainty `possible`, or a relaxation set passed over).
  - *The split* (for `first`; mirrored for `last`). Order the possible targets by earliest start. A target is *blocked* when another step's candidates include it (an `any` step whose concept it carries, a certain ordered step whose event it is, an unsafe ordered step among whose possible targets it is), and m counts the steps that block one. λ is the least earliest start at which the targets starting no later include an unblocked one, or more than m blocked ones. The candidates are a point over [λ, least latest start], and the blocked targets with earliest start below λ, as themselves.
  - *Order facts,* on starts: a covered step on concept K starts at or before (for `last`, at or after) any other step bound to one of the patient's events carrying K; a `first` step starts at or before a `last` step when some event carries both concepts; a `first` step starts at or before another `first` step whose concept's events all carry its concept, and a `last` step at or after another `last` step likewise.
  - *Why `exact` and `none` are sound.* In every choice of times the true target is a possible target, its start lies in the envelope, and it starts at or before every event of its concept (over `Times.dom`, which already carries shared variables and `proper`). Give each point the true target's start and keep every other time: every constraint reads the same value, since a covered step's end is read only for points, and another step bound to the target itself reads that same time. So a binding exact over the points is exact; and for the possible phase, a true target starting at λ or later maps to the point, one starting before λ is blocked and is a candidate itself, and the order facts hold. So the possible phase's model has a binding wherever the truth has one, and its `none` is sound. The facts only remove choices; leaving them out would still over-approximate.
  - *Why no `none` of the two searches is lost.* A binding on the point at time v can be moved to a target that starts no later than λ, whose latest start is at least the envelope's upper end (so at least v), and that no other step binds (there are more of them than steps that can bind one); its variable is its own and its end is not read. So the repeated search would find a binding too.
  - *Relaxations, costs, budgets, `complete`.* The search is per relaxation set, on that set's concepts and bounds; the order of sets and the notes for an undecided set are as above. Each phase has the query's search budget; a stopped phase concludes nothing and the set is reported as a stopped search. `exact` and `none` carry `complete: true`. Two steps on one concept and occurrence share their point (one target in every choice of times). In the exact phase that is by construction (the point is cached per concept and occurrence); in the possible phase it holds because the two steps' blocked sets and counts are symmetric (each blocks the other's possible targets), so the split's cache key is the same, not because the split is shared by construction.
  - *The order facts in the exact phase (D31, second attempt).* Where the exact phase without facts finds nothing and the possible phase found a binding (or stopped), the exact phase runs again with the facts that can apply to its candidates: the `first`/`last` facts between ordered steps, and a covered step's fact on an `any` step or a certain ordered step bound to an event carrying its concept (a point is an event of no one, so no fact conditioned on one applies to it). Certainty is then decided jointly, not pair by pair, since through a third step a fact can bound a pair it does not name: for a full binding, the network over its variables (their ranges and the distances between linked ones), the points' ranges and the facts the binding meets; a constraint is certain when the network's bounds on its difference lie within it. Every true choice of times maps into the choices that network allows (each point takes its true target's start, and every fact holds there), so a binding certain over them is exact. Domains are pruned by the pairwise plausibility tests with the facts, prefixes by joint feasibility; the search has the query's budget. "The first K, then the last J at least 0 later", with an event carrying both, is now `exact`.
- **Why linked variables are unsafe.** That a time constraint on the picked event also holds at the true target's time needs the picked event's variables to be its own: with a shared variable, its range is tied to another event's, and the true target's time need not satisfy the tie.
- **Where ends are read.** Only the grace half of `during` reads a step's end; scope and `after` read starts. A point's end is its start.

## Decision procedure

| Question | Trajectory shape | Method | Cost per patient |
|---|---|---|---|
| Exact | Forest (relations between steps form no cycle) | Arc consistency on the pairwise certainty relation over candidate events, then a backtrack-free assignment (Freuder 1982) | Polynomial, O(*e* · *n*³) with AC-3 |
| Exact | Graph with a cycle | Arc consistency, then backtracking over the remaining candidates | Bounded by `search_budget` |
| Possible | Forest, every candidate a point event | Arc consistency on pairwise plausibility, then dynamic programming over unions of time intervals: leaves restrict their parent's start times to those that can reach a child time, and a top-down pass takes the latest admissible time at each step. If the binding found puts two steps on linked variables, it is checked against the joint network, and searched for as below if the check fails | Polynomial, unless the check fails |
| Possible | Cycles, or exposures (start and end chosen together) | Arc consistency, then backtracking that checks each partial binding's temporal network (`temporal_stn.py`) | Bounded by `search_budget` |

Arc consistency is always sound pruning: an event without support for some relation cannot be in any binding. That holds with shared variables, because both pairwise tests read the patient's network. A possible binding's times satisfy the network and each constraint, so every constraint is plausible for its pair of events. Exactness is a conjunction of tests that each depend on two variables. On exact times it is often decisive even on cycles. For example, B and C each 1–2 days after A but exactly 10 days apart propagates around the cycle until every domain is empty.

The interval programme chooses each step's time independently. Steps whose events share a variable, or are linked through an exposure's start and end, are coupled in fact. The programme solves a relaxation of the problem: every true solution is one of its solutions. So its "no binding" is a sound refutation. A binding it finds stands as found only when no two steps' variables are linked. Otherwise the binding is checked against the joint temporal network and, if that fails, the question goes to the bounded search, which is exhaustive. Each answer is either refuted by a relaxation, verified by the exact network test, or searched, so the method is sound without having to reason about couplings inside the programme. The method reports `point_forest_intervals_checked` when the check confirms the binding, and `bounded_backtracking` when it falls back.

Why the polynomial cases stop where they do:

- Exactness is a binary constraint over event choices, so the classic result for tree-structured constraint problems applies for every step kind.
- Possibility on point events can also be read as max-closed constraints over time variables (engine design §7.2). On a cyclic graph, though, propagation can shave a domain one grid point at a time, so its cost grows with the length of the time ranges, not with the number of events.
- An exposure's start and end are chosen together, which breaks max-closure (engine design §7.3).

Those cases are searched, under a budget, and an exhausted budget is reported as `unresolved`.

Each result names its `method` and whether it is `complete`. A possible result carries a witness start time for each step.

## Verification

`patterns/test_trajectory_graph.py` has 48 tests:

- **Semantics.** Exact and possible sequences, first occurrence, `during` with grace and an ongoing exposure, scope and anchors, exclusion, and cost-ordered relaxation.
- **Methods.** A six-step tree with 300 candidates per step (300⁶ bindings) decided by propagation with a search budget of 1. A cycle searched. An exhausted budget reported as unresolved, with the relaxed match beside it. A contradictory cycle refuted by arc consistency alone. Two relations on one pair that leave it no gap (C during the point A, and at least 3 days after it) give no match; the interval programme used to crash on them.
- **Shared times.** One uncertain event bound to two steps cannot take two times: the engine before this rule called "B at least 5 days after A" possible on a single event, and the answer is none. `after` from 0 to 0, or a step during its own exposure, is exact on one event. Events naming one `start_var` share its time and the intersection of its ranges. An exposure orders the variables it names even when it is not bound. A forest binding that gives one event two times is caught by the joint check, and search finds the binding that works.
- **Proper events (D24).** If Y starts when a proper X ends, `after` from 0 to 0 is none and `after` at least 1 is exact; without `proper` both are possible. A lone proper exposure narrows only its own ranges and links no other variable. `proper` on a point, a non-boolean `proper`, and a proper event that cannot end after it starts are refused by name, on the trusted path too. `proper: false` decides byte for byte as an absent `proper`, on 300 differential cases.
- **First and last (D30).** `trajectory_graph_worlds.py` checks results against what they mean, by enumerating every choice of a patient's times on small grids: in each choice the target of a `first` step is the event that starts earliest (ties by the order), and a result is sound when what it claims holds (`exact`: its binding holds in every choice; `possible`: in some, and no binding in all; `relaxed`: the query and every cheaper set hold in none; `none`: no set within the budget holds in any; a match beside `unresolved`: its certainty). The nine review cases (seven from the review of the D30 draft, two from the review of D30 itself) are decided as the semantics require. The engine before D30 got the first seven wrong (six by a wrong status, one by calling `possible` a query that holds in every choice). D30 as first built got the last two wrong, because it took another uncertain step's picked event, not its possible targets, as the only coupling. *What the check covers:* seeded small cases of two to four events, each of concept x, y or both (so that two steps' families overlap without nesting), with overlapping ranges, exposures, proper events and shared variables, one to three steps, `after` and `during`, anchors, scopes and two relaxations. The test runs 3,000 cases; an ad hoc run of 20,000 had no violation, and the review's targeted fuzz over overlapping families none in 20,000. The engine and the reference have no violation and agree; the frozen engine from before D30 has violations; each part of the rule, undone, produces violations: the rule switched off, coupling ignored, coupling read from picked events only, a relation reading the end ignored, or shared variables ignored. Larger cases rest on the reference and the arguments above. On exact times `last` picks the event it picked before.
- **One envelope search (D31).** The worlds check finds no violation on the test's 3,000 small cases, 1,500 cases of two or three mostly ordered steps over overlapping families (after the D30 review's targeted fuzz) and the review cases, and the reference, which writes the envelope search again (coverage, blocked targets, λ, points and order facts by its own satisfiability tests), agrees on every one; an ad hoc run of 20,000 of each kind had no violation and no disagreement. Against D30 (`_ENVELOPE` off) every changed result starts undecided and ends decided or still undecided. Four planted defects are caught by the worlds check: a fact reversed, a conditional fact applied to every event, the split's point without the blocked targets below λ, and an exact claim made on the split. Dropping the facts cannot make a result unsound, so the worlds check cannot see it; the reference does, and so does the D30 review's M1 case "the last J strictly before the first K", now `none`, which needs a fact. With the facts in the exact phase too (D31, second attempt) the review's other M1 case, "the first K at or before the last J", is `exact`; against the first attempt (`_EXACT_FACTS` off) a result moves only from undecided to `exact`; an exact-phase fact reversed, or a conditional one applied to every event, is caught by the worlds check, and leaving the facts out is caught by the reference (which adds the facts a binding meets to the patient's own and decides each constraint by Bellman–Ford over all of them) and by that case.
- **Cost levers (D30 review).** Three changes that cannot move an output are switched by `_LEVERS`: arc consistency's common case by a sorted sweep (O((n + m) log m) per arc instead of O(n·m)), handling an event that is in both domains as before; the second search of an unsafe step without its exact phase, since it only asks whether any binding exists; and the certainty test for a family with no shared variables by comparing range ends. With them on and off, `match` and `decide` are byte-identical on the differential, the kernel comparison's wide cases, 3,000 worlds cases and the review cases.
- **Validation.** Queries and patient records outside the profile are refused by name, including malformed time variables, shared variables no time satisfies, and linked variables beyond the limit.
- **Example.** The committed example (`examples/trajectory-graph/`) gives one patient of each outcome.
- **Differential.** 1,500 seeded random trajectories: chains, trees and graphs with a cycle, with point events and with exposures. Steps often share a concept, so one event is often bound to several steps. In about a third of the cases some events name another's start or end variable, sometimes with a different range. In a quarter of the cases a second relation is placed on a pair that is already related, sometimes contradicting the first. The engine and `trajectory_graph_reference.py` must agree on status, certainty, relaxation set and cost (and since D30 on an undecided result's reason, what it reports beside it, and whether a relaxation set was passed over), and every binding the engine reports must have the claimed certainty under the reference's own test. Of the 2,400 cases, 68 are unresolved by the order rule, and in 13 a relaxation set was passed over. A further 900 cases (chains, trees and graphs) use proper exposures that could otherwise end as they start (739 of the cases have one). In 682 an event starts when an exposure ends, often between events two related steps can bind, and `after` bounds sit near zero and `during` graces at zero.

The reference enumerates every binding. It shares no decision code with the engine: candidate selection, the order rule (certainty, envelopes and possible targets by satisfiability tests over the whole patient), the constraint semantics and the time model are written again. Because it implements the same rule, a defect in the rule itself would reappear in it; the worlds check above, which defines the semantics instead of the rule, is the evidence that the rule is sound. The frozen-engine comparison of D21 (`KernelIdentityTests`) is made on the cases D30 cannot touch (no uncertain target, `last` picking the same event), which remain the majority in every comparison. Its tests run Bellman–Ford over the whole patient's variables. A binding is possible if the patient's facts and the constraints are jointly satisfiable. It is exact if, for each constraint, the facts with that constraint's negation on the integer grid are unsatisfiable. Planting a defect in the engine's interval propagation, or using certainty where plausibility belongs, makes dozens of differential cases fail. So does giving each step its own copy of its event's variables, the modelling before shared times: 140 of the 1,500 cases fail. On the 900 proper cases, dropping `proper` changes the reference's answer in 16, and an engine that ignores it (a 0 edge where −1 belongs) disagrees with the reference in 15. With the pairwise kernel's closed form refused everywhere, every proper case decides byte for byte as with it. The reference adds `proper` independently: its facts give a proper event an edge of weight −1 from end to start, where other events have 0.

## Not in this profile

- An adapter from SULO claims or the execution store. The SULO adapter is a separate module: see [trajectory-graph SULO adapter](trajectory-graph-sulo-adapter.md).
- Event-count steps and measurement conditions; callers supply them as derived concepts or events. The [execution store](execution-store.md#value-conditions-d28) does this for value conditions (D28): it compiles each condition on a step into a per-query tag concept, which the events satisfying the condition list, and a value relaxation into a `widen_concept` to a wider tag. The engine and this profile are unchanged by it, and a tag is a concept like any other here.
- Distinct events across steps, disjunctive relations, nested "while taking" and absence (engine design §7.3).
- Clocks: every time is on one comparable grid.
