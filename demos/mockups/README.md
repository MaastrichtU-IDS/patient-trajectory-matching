# Interface mockups

Exploratory interfaces for clinical researchers defining and matching patient trajectories, for design discussion. Nothing here is product code, a supported profile, or a clinical claim; the product is the research workspace in [`app/`](../../app/). The test data is a synthetic paediatric rare-disease cohort.

```sh
python demos/mockups/synthetic/generate.py                 # writes demos/mockups/data/ (git-ignored)
python demos/mockups/server.py                             # pages plus the trajectory-graph engine on 127.0.0.1:8090
# from another machine: ssh -N -L 8090:127.0.0.1:8090 <user>@<host>, then open http://localhost:8090/
```

Opening the HTML files directly will not work; the pages fetch the dataset over HTTP.

`server.py` serves the pages as `python -m http.server` would, and adds the trajectory-graph engine (`patterns/trajectory_graph.py`, [profile](../../docs/trajectory-graph-profile.md)) and, since D37, an execution store of the synthetic cohort. The trajectory page matches in that store by default ([below](#the-trajectory-page-on-the-store-stage-2)). A toggle switches to the engine on the page's own candidates (the page resolves each step's candidate events, including relaxed alternatives, and the engine decides timing, relaxation and search budgets) or to the page's own in-browser search, which is also used wherever no server is reachable, as on static hosting. `test_engine_parity.cjs` checks that the engine and the in-browser search give every patient the same status, certainty and relaxation set. Given a locally built MIMIC-IV demo store, `server.py` also serves the store query page ([below](#store-query-page-stage-1)).

## The trajectory page on the store (stage 2)

Since D37 (D29's stage 2) the trajectory page matches in the [execution store](../../docs/execution-store.md) by default. At startup `server.py` builds the cohort the page downloads into a store, with the converter itself emitting series and the diary's period label (`store_parity.build`, as the parity test builds it). The build takes about a second and goes into a temporary directory, removed when the server closes cleanly or on SIGTERM, SIGINT or SIGHUP (never on SIGKILL, which no process can catch); `--trajectory-store-root DIR` (or `PTM_TRAJECTORY_STORE_ROOT`) puts it elsewhere, never inside a git working tree, and `--no-trajectory-store` leaves it out. Without a store the page says why (for example `STORE_DEPENDENCY_MISSING`) and matches with the engine.

- **Endpoints** (`store_trajectory.py`):
  - `GET /api/trajectory-store/status` names the snapshot, its profiles and its 48 patients, or says why there is no store (no cohort generated, DuckDB missing, ...);
  - `POST /api/trajectory-store/match` takes the page's query as its translator writes it (`trajectory/store_request.js`): `{query, conditions, windows}`, times in whole minutes from each patient's birth. It answers with `store_conditions.match` (D38, the one entry point), which routes a gene step's request to `store_conditions_gene` and every other to `store_conditions_relative.match`, which hands every request but a rise's to `execution_store.match` unchanged: per patient, the store's status, certainty, relaxations, cost, reason and steps, the bound records described from the store's own rows (kind, source, record, recorded times, value) and the witness times, in minutes from birth.
- **Per-patient answers, for synthetic data only.** Unlike the MIMIC endpoints, these answer per patient: the data are synthetic, and the page already holds every record. The store is served only if the cohort's dataset id is the generator's and the built snapshot's dataset id and patients are exactly those of the cohort file the server serves. The MIMIC endpoints and their aggregate-only rules are unchanged.
- **Named refusals.** A request whose shape is wrong gets a named 400 (times must be whole minutes, as integers, so no string or float reaches the conversion); a request the store or the engine refuses gets their code; an internal failure `500 INTERNAL_ERROR`, with no detail.
- **One translator.** The page sends the request its own translator writes, not its definition for a server-side port. The translator reads the page's state (the index windows it places, the parent concept or drug class each relaxation names, the costs), and the parity test pins it; a port would be a second copy that could drift.
- **What the page shows.**
  - The results panel says which backend answered: *Answered by the execution store* with the snapshot and profiles, or *In-browser fallback: CODE* with what the code means, or *Matched by* the engine or the page.
  - The store's statuses as given: exact, possible, relaxed with its cost and relaxations, unresolved (labelled *undecided*) with its reason and any relaxed match beside it, no recorded match with any note, not comparable with its reason and steps, and no index period with the page's own reason.
  - The detail drawer lists the records the store bound (source, display, the letter's date for a mention, record id), their recorded ranges and the witness times. It does not re-check the store's certainty. Where the page's own search answers differently for that patient, the drawer shows that answer too, with the declared causes that can explain it; the store's answer is the one shown.
- **Fallback.** A query the translator refuses (below), or one the store refuses by name, is matched on the page's own candidates (with the engine where it is reachable), labelled `in-browser fallback: <code>`. Without a server the page matches in the browser, as on static hosting.
- **Tests:** `test_store_trajectory.py` (the endpoint's results equal `store_conditions.match` called directly, a gene step's point described by its genetic result, times in minutes exactly, bound records from the store's rows, every refusal named, the content check, the build removed on close); `test_store_parity.cjs` (every page template answered or refused by name, and an option sweep).

## Store query page (stage 1)

`store-query/` runs trajectory queries in the [execution store](../../docs/execution-store.md) on the server, against a store built on this machine from the open MIMIC-IV demo. It sits beside the other pages (D29, stage 1); since D37 the trajectory page itself matches in a store of the synthetic cohort ([above](#the-trajectory-page-on-the-store-stage-2)).

```sh
python -m pip install -r patterns/requirements-store.lock.txt
python -m patterns.mimic_store_ingest --input-dir data/local-mimic/icu --dataset-id mimic-iv-demo-2.2 --chartevents --workers 8
python demos/mockups/server.py --port 8091 --mimic-store verification/execution-store-mimic-run/store \
  --mimic-d-items data/local-mimic/icu/d_items.csv.gz
```

The build takes about two minutes and writes into the git-ignored `verification/execution-store-mimic-run/`. The demo files come from `data/local-mimic/` (D11). Neither is ever committed. `PTM_MIMIC_STORE` and `PTM_MIMIC_D_ITEMS` can stand in for the two flags. Without a store, the page says so and shows these commands. Without a server (static hosting, or the file opened directly), it says the query needs one.

- **Endpoints** (`store_query.py`):
  - `GET /api/store/status` says whether a store is available, and if not, why;
  - `GET /api/store/catalogue` lists the store's item classes and dictionary categories, with patient and event counts and the units recorded for each;
  - `POST /api/store/match` takes the page's query and runs `execution_store.match`.
- **Aggregate counts only** (D17 and the demo convention), enforced on the server. The match answer is built field by field from counts: counts by status, `not_comparable` and `unresolved` reasons, notes, relaxations used, candidate, filtered and pruned counts, and timings. It is then checked against a closed schema: only known keys, integer counts from 0 to the store's patient count, and strings from fixed vocabularies (statuses, upper-case reason codes, the server's own relaxation identifiers). The reason, note and certainty keys are also compared with the patient identifiers. Nothing the page sent is echoed. The status and catalogue answers are checked against closed schemas too. An answer that fails its check is never sent; the server answers `500 AGGREGATE_RULE_VIOLATION` instead. A malformed request gets a named 400, and an internal failure `500 INTERNAL_ERROR`, with no traceback. No patient identifier, time, value or per-patient row leaves the server.
- **Only the open demo, by content.** The manifest's dataset id (`mimic-iv-demo-2.2:source_item_class`) is a first, cheap filter only: it is a label outside the snapshot identity, and the build command above writes it whatever the input. Before anything is served, the store must hold exactly 100 patients whose sorted identifiers hash to `DEMO_SUBJECTS_SHA256` in `store_query.py`. That digest is pinned from the demo's own `icu/icustays.csv.gz` (itself pinned in `data/mimic-inputevents-demo-pin.json`); `python demos/mockups/store_query.py demo-pin data/local-mimic/icu` recomputes it. A relabelled snapshot, or full MIMIC-IV built with the demo's dataset id, is refused.
- **Counts-only is not disclosure control.** There is no small-cell suppression, and differencing works: a run of queries that halve a threshold can isolate one patient's value. That is acceptable only because the data are the open demo. A credentialed deployment would need real disclosure control (suppression, noise or query auditing), which is not built; the content check is what keeps credentialed data out of these endpoints.
- **The query builder.**
  - *Steps* are item classes or whole `d_items` categories. They are source item classes labelled with the public dictionary's terms, not clinical concepts, and the page says so.
  - *Each step* takes an occurrence (any, first or last) and an optional value condition: a unit chosen from those recorded for that item, a lower bound (`>` or `≥`) and an upper bound (`<` or `≤`).
  - *Relaxations*, optional: a wider threshold (`widen_value`, which the store refuses unless it contains the stricter one), or any item in the step's category (`widen_concept`).
  - *Constraints* are *starts between min and max after* (minutes, hours or days, with `extend_max` as a relaxation) or *happens while* an infusion runs, with a grace (with `extend_grace`).
  - *Thresholds* are kept and sent as the strings typed. The server refuses a JSON number (`THRESHOLD_MUST_BE_A_STRING`), so no threshold passes through a float.
- **The index period** is placed on the server from the store's coverage table. That table holds one period per ICU stay: `icustays` in-time to out-time, widened to the stay's own records. The page offers three rules: the first ICU stay, its first 24 hours, or from the first stay's start to the last stay's end. This is a simple choice, not the demo differential's seeded random windows. A patient with no stay has no period.
- **Results** explain each status and why most results are `not_comparable`. Only numeric chart rows with a unit and continuous infusion segments are admitted. An excluded row of a step's item that the scope admits might have matched (D18), whatever the value condition (D28).
- **Examples.** Each is checked against the catalogue before it is offered. Their aggregate results on the demo store (snapshot `c4f41d29…` since D30; the results are those of `9730e87b…`, unchanged):

| Example | Exact | Relaxed | Unresolved | None | Not comparable | Candidates, pruned |
|---|---|---|---|---|---|---|
| Non-invasive mean blood pressure below 65 mmHg, then norepinephrine 0–6 h later, first ICU stay (relax to below 70, or any Medications item) | 13 | 0 | 38 | 6 | 43 | 70, 15 |
| Heart rate above 120 bpm while the first norepinephrine infusion runs, first ICU stay (relax to above 110) | 3 | 0 | 1 | 81 | 15 | 24, 6 |
| First temperature of at least 100.4 °F, then respiratory rate above 24 within 4 h, first 24 hours (relax to 8 h) | 11 | 1 | 0 | 85 | 3 | 28, 14 |

  Every `not_comparable` and `unresolved` result above has reason `ADMISSION_EXCLUDED_RECORDS`. In the first example, 36 patients match only if norepinephrine is widened to any Medications item, and 7 only if the threshold is relaxed. Excluded rows could hold an unrelaxed match for those patients, so their relaxed match is reported beside an `unresolved` status. Each query takes 0.1 to 0.2 s.
- **Tests** (`test_store_query.py`) build stores from the synthetic MIMIC fixture, never from real data. The fixture is served only with its own pin passed in as a test hook. Under the real pin, every one of these is refused: the fixture built under the demo's dataset id, the fixture under a credentialed id, a relabelled snapshot, and 100 patients that are not the demo's. A real demo store passes when one is built locally (the test is skipped otherwise). The tests also check:
  - a failed open leaves nothing open, and missing DuckDB is named;
  - malformed requests (lists for strings, enormous numbers, deep nesting) get named 400s, and an internal failure a 500 without detail;
  - the answer's keys and values are counts only, bounded by the patient count, with no patient identifier, event time or value, and the status and catalogue answers pass their own schemas;
  - a deliberately leaky answer becomes `500 AGGREGATE_RULE_VIOLATION`;
  - the counts are `execution_store.match`'s own;
  - thresholds must be strings and are compared exactly;
  - units come from the store;
  - each refusal is by name.

## The synthetic cohort in the store: parity with the trajectory page

`test_store_parity.cjs` (Node, run in CI) puts the 48-child cohort into a store. Since D44 each Python helper it starts reads its input from a regular file, never a pipe, and fails after 30 minutes instead of blocking (the `store_parity.py sweep` helper once sat in its read of stdin for about 30 minutes; no cause was found). It compares, patient by patient, the store's results with the engine's results on the trajectory page's own candidate resolution. The twenty-six trajectories (ten from D29, four from D32, the three rise templates restored in D36, the Blank template since D37, Tree and Graph with their gene step since D38, four templates under "coded only" since D39, and Tree and Graph with their gene step under "coded only" since D42, through the joint profile) are ones the page can express in the store's language, translated by `trajectory/store_request.js` (D32):
- concept steps with any, first or last; since D32, Nth and Nth-from-last occurrences and "at least N times within a span" or "in the index period", with the one-fewer relaxation (four trajectories, among them the page's *Event frequency* template), over coded records only (the page's "coded only" setting). D37 kept three of the four on D32's reading (`codedOnly: 'derived'`: coded only for the derived step, stated findings elsewhere). Since D39 all four run with every step over coded records, through the store's profile 1.3 (`codedOnly: 'store'`, `patterns/store_conditions_coded.py`), as do four more trajectories: Sequence, Tree and Graph without their gene step, and Blank, under "coded only";
- `after` and `during`, and an anchor on the period's start;
- the page's index windows;
- absolute value conditions, one with a threshold equal to recorded values (whole monthly counts), so reading "at least" as "above" changes 10 results;
- the page's relaxations: a parent concept, the drug class, a 1.5× longer gap, 30 more days after stopping, and a looser threshold.

How it works:
- **Node.** The page's candidate resolution is JavaScript. The test runs the page's own `core.js` and `trajectory/app.js` in a stub DOM, as `test_engine_parity.cjs` does, rather than a port that could drift from it. Node is not installed on the development machine, so the test was run there with a portable Node 20, downloaded into a scratch directory and checked against nodejs.org's published SHA-256. CI runs it with `actions/setup-node`.
- **The store side** (`store_parity.py`) builds the cohort with `patterns/synthetic_ingest.py` emitting `series` (its option since D32): each measured record with a number and a unit gets one `series` row, the value spelled as the cohort's JSON writes it, and the 31 measured records without a unit become excluded records. Since D38 it converts through the wrapper of `patterns/store_conditions_gene.py`, which adds each genetic result's reports and classifications to its evidence (and the label `gene_report_kinds`), and it matches through `patterns/store_conditions.py`. Windows are the page's, sent in its engine's minutes from birth, which map exactly onto the store's clock.
- **The translator** (`trajectory/store_request.js`) refuses by name what the store cannot express: hedged free text (`FREE_TEXT_HEDGED_UNSUPPORTED`), an Nth occurrence or a count over stated free text (`FREE_TEXT_COUNT_UNSUPPORTED`: the store ranks and counts coded records only), and "while taking" from an Nth step (`NTH_STEP_HAS_NO_END`). Since D36 it translates rises and falls by default, as the store's relative conditions (`patterns/store_conditions_relative.py`); a caller can still ask for the named refusal (`RELATIVE_CONDITION_UNSUPPORTED`). Since D37 it also refuses "coded records only" on a query with a step that is neither an Nth occurrence (N > 1), a count nor a measurement (`FREE_TEXT_CODED_ONLY_UNSUPPORTED`: the store reads the converter's letter mentions for every such step, so the option would silently become "also stated findings"), and a threshold or factor that does not print as a plain decimal (`VALUE_NOT_A_PLAIN_DECIMAL`). Since D38 it translates gene steps by default, as the store's gene condition (`patterns/store_conditions_gene.py`: each coded genetic result of the gene, at its first report that is not negative, across reclassification, timed by its recording); a caller can ask for the named refusal (`GENE_CLASSIFICATION_UNSUPPORTED`). It refuses an occurrence on a gene step (`OCCURRENCE_ON_GENE_STEP`), and a gene step under "coded records only" (`GENE_WITH_CODED_ONLY_UNSUPPORTED`) unless the joint profile is in force (D42: `options.codedOnly: 'store'` with `options.geneCodedOnly: true`; the default since D49, `STORE_GENE_CODED_ONLY`): then the request is profile `execution-store-conditions-gene-coded-1.0`, gene steps as D38 and every other step over coded records as D39, answered by `patterns/store_conditions_gene.py` through D39's hooks in `patterns/store_conditions_coded.py`. Since D39 the store can leave letter mentions out of every step (profile `execution-store-conditions-1.3`, `exclude_kinds: ["mention"]`), and the translator writes "coded records only" that way (`options.codedOnly: 'store'`). D39 did not make it the default: it missed its usefulness bar on the Event frequency template (decision log). D43 built and checked a store-side refinement that decides the counts behind Event frequency's undecided results, but did not ship it (its latency rule missed as written; decision log, D43). D43b retried it in the store's worker pool and did not ship it either: its count requests through the dispatcher were too slow at 300,000 patients (decision log, D43b). D43c pruned the witness search and shipped it (decision log, D43c). The page's server, which calls the dispatcher, now gets those counts decided: nine parity results are pinned as decided, and the totals are unchanged. D45 measured turning "coded only" on by default (with the joint profile) and found it ready: `coded_default.cjs` loads the translator with the two constants turned on and checks that only "coded only" changes. **Since D49 both are on** (`STORE_CODED_ONLY` and `STORE_GENE_CODED_ONLY`, the owner's decision): under "Coded records only" the page sends profile 1.3, or the joint profile with a gene step, and every page template is answered by the store. `codedOnly: false` (or `null`) still asks for `FREE_TEXT_CODED_ONLY_UNSUPPORTED`, `'derived'` for D32's reading and `geneCodedOnly: false` for `GENE_WITH_CODED_ONLY_UNSUPPORTED`; the page sends none of them, and has a message for each (decision log, D49; `d49_flip.cjs` checks that only "coded only" moves, into the requests D45 measured). The evidence options read "Coded records only", "Coded records + findings stated in clinical notes" and "Coded records + uncertain findings in clinical notes (e.g. 'possible', 'suspected')", with a note that the first reads no clinical note for any step. The test asserts each code, on the page's own templates where they apply. The page sends the translator's request to the server (D37; no server-side port).
- **A replay** runs the engine alone on the candidate events the explanation reads, deriving Nth and count steps from them by the store's own rules. It must give the store's own result, up to the store's comparability and excluded-records rules. It does, for every patient: the store matched exactly those candidates. So each difference comes from which events are candidates, from the comparability rules, or from a derived step's rule. None comes from translating the query or the windows.

**Results** on the committed seed (D35): 557 of 672 patient results agree over the fourteen trajectories (555 before D35, which decided C004 and C015, below). The ten of D29 give 399 of 480 (401 before D32: four weight results moved, below; 397 before D35); the four with Nth occurrences and counts give 158 of 192. The 115 that differ each have a named cause, from a closed list the test checks. The causes are pinned per trajectory and patient in the test, so a new or vanished difference fails. The classifier lists every step whose candidates differ between the two sides, so a patient can have several causes, and the counts below are patients per cause over the fourteen trajectories.
- *Coverage* (19 patients, one trajectory). This one is the store's comparability rule, not a page shortcut. The store says `not_comparable` (`NO_SOURCE_COVERAGE`) when no source recording a step covers the period; here that source is the seizure diary. The page says *no recorded match* when the steps that can be measured do not match, and *not comparable* only when they do.
- *Letter mentions* (81; 58 of them in the ten D29 trajectories). The store holds each finding a letter states as its own event. Since D30 that event ranges from the patient's birth to the letter, since the letter says only that the finding happened by then; before D30 it was timed by the letter itself, which missed the true time of 2,443 of the 2,444 mentions. The page merges a mention into the event it describes, or times it from the letter's wording ("about 3 weeks ago"). A letter's mention of a medicine counts here too.
- *Record reconciliation* (67; 40 in the ten). The store holds every record as an event. The page merges the records of one happening, grouped by its stated rule (`reconcile_v1`, since D47; by the generator's truth before), and times the merged event by its most precise record. So the first or last event can differ, and so can whether a time is certain. In C004, for example, the most precise record of the first febrile seizure has a year typo, which moves the page's merged event to 2091. The store still holds the registry's record of that seizure.
- *Medication records* (64; 41 in the ten). The store's exposures run from each order to its stop, and an ongoing one has an open end; dispensings are separate point events. The page builds one exposure per course, from the order or else the first dispensing. It ends at the stop or when the supply ran out, and an ongoing one ends at last contact or later.
- *Measurement records* (4, D32). The converter makes the 31 weight, height and head-circumference records without a unit excluded records (a source that drops a value must say so, D28). The page reads them by value alone. So "weight at most 9 kg" is not comparable in the store for three patients (an excluded record of the item could have matched) and unresolved for one (it could have supplied the unrelaxed match).
- *Occurrence envelope* (14, D32). For an Nth step the store's time is the Nth occurrence's, ranging over every time the coded records allow, and unresolved where another step can bind the ranked events. The page binds the happening its most precise record ranks Nth, which is not sound under uncertain times (D32 plan, 1.2).
- *Count timing* (20, D32). For a count the store binds the record at which the count is reached, certainly or only possibly, with the two-pass rule (unresolved where it cannot decide). The page takes each run of N consecutive happenings, by their best dates, that may fit the span. Records against happenings (record reconciliation) adds to it: the store counts recorded events, so a happening recorded twice counts twice.
- *Order uncertain* (0 since D35; 9 in D30 to D34). A `first` or `last` step whose target the records leave uncertain is decided in the store on the range the true first (or last) time can take, where that is exact, then by the target split over its possible targets (D35), and is otherwise `unresolved`. Before D35 the first blocker in "a seizure while taking the first blocker", whose end the relation reads, left 9 of its 10 candidates unresolved; the split decides all ten (`possible`), so C004 and C015 now agree with the page, and the other seven differ by letter mentions, medication records and record reconciliation only. The page binds the event its reconciled records date, without that test.

D30 moved 57 of the store's results: 53 at the mention-timing stage and 4 at the order-rule stage (none at the corrected `last`). Each was localized to a stage by running the store as before D30, then with each change in turn; the stages are cumulative, so the order rule acting on the wider mentions is counted at the mention timing. With the mention timing localized before the order rule instead, 59 results move at some stage: 45 at the mention timing only, 2 at the order rule only and 12 at both. The localization does not by itself show that a change is a fix; the engine's worlds check does that. The page now also takes `last` by the latest possible start, then the earliest, as the engine does.

With D35 the counts per cause are: count timing 20, coverage 19, letter mentions 81, measurement records 4, medication records 64, occurrence envelope 14 and record reconciliation 67 (with D32: letter mentions 83, medication records 66, order uncertain 9 and record reconciliation 69). The Nth and count trajectories ask for coded records on the page, while the store's other steps still read letter mentions, which adds letter mentions there.

*Unresolved in the store*, per trajectory: 0 of 39 results with a window for "a seizure while taking the first blocker" (9 from D30 to D34; the target split of D35 decides all ten of its candidates `possible`), 1 of 39 for the weight trajectory, 1 of 38 for the *Event frequency* template, 0 of 38 for the second seizure and the second-to-last seizure, and 8 of 38 for "at least 2 febrile seizures in the index period" (the count reached only possibly); 0 elsewhere.

## The synthetic cohort

`synthetic/generate.py` is standard-library Python and deterministic for a given seed (`--check` regenerates and compares). It writes 48 invented children across Dravet syndrome, GEFS+, febrile seizures, PCDH19 clustering epilepsy, CDKL5 deficiency disorder, tuberous sclerosis complex, Rett syndrome and spinal muscular atrophy.

Each child has two layers:

- **truth**: what happened, in days of age, with no recording artefacts
- **records**: what nine sources hold (hospital EHR, clinic letters, a Dutch referral letter, a Belgian discharge summary in French, the genetics laboratory, the pharmacy, a parent seizure diary, an ERN registry and newborn screening)

Every record keeps three times apart: when it happened (bounds and precision), when it was written down, and when a researcher's system could first see it. Every deliberate departure from a clean capture is listed in the child's `quality` array with the records and truth event it touches. The 32 kinds fall into five groups:

| Group | Kinds |
|---|---|
| Missing | measurement, unit, result, follow-up gap, lost to follow-up |
| Incorrect | unit error, decimal shift, implausible value, year typo, day–month swap, duplicate, copy-forward, wrong code, sibling's record |
| Timing | approximate onset, conflicting onset, recorded late, start known only from dispensing, approximate stop, result reported weeks after collection, reclassified variant, corrected age |
| Coding | broader parent code, local code only, several terminologies, free text only |
| Free text | negation, family history, plans, hedging, Dutch or French, misspelling |

The reference child, C001, is scripted: a girl with Dravet syndrome whose first seizure was at a regional hospital, who was given carbamazepine there before her SCN1A variant of uncertain significance was reclassified as pathogenic, and whose records carry one or more instances of most kinds. Sodium-channel blockers raise seizure counts only in the Dravet children, so a rise after exposure carries signal.

Terminology codes are illustrative and were written from memory to make coding variation concrete. They have not been checked against a terminology release.

## B · Start from a patient

`patient-first/` follows the progressive disclosure in [specification 2.2 §20](../../addenda/specification-2.2.md): reference history, explicit criteria, ranked candidates, pairwise evidence and revisions. It computes everything in the browser from the records:

- **Index window.** Each patient is compared over their own window, placed by one rule. Each end is set at birth, at an age, on a calendar date, at the first occurrence of any event chosen by terminology search (with an offset), or as a length of time from the other end. Every amount of time takes a unit from seconds to years; ages are fractional days, so a time of day on a record counts. Findings count if they occurred inside the window; diagnoses and genetic results are states and count if established by its end, using the classification reported by then; medicines count if taken at any time during it. By default only evidence *available* by the end counts, so a letter signed later or a result filed later is excluded. A patient whose window cannot be placed (no start event, born after it ends, not followed to its end) is listed as not eligible with the reason. The pairwise drawer can align two patients by age, window start or window end.
- **Must match, Prefer similar, Ignore, Hide from view.** Only Must match changes who is eligible; only Prefer similar changes the order; Hide changes the page and never the computation. Unrecorded features score zero and are shown as coverage beside the score.
- **Hide from view is one rule everywhere.** Hiding an event hides that concept, for every patient, on the timelines, the event list, the criteria summary, the results, the pairwise table, its data-quality column, hover tooltips and annotated mentions in letters. Hiding a feature hides that whole kind of information the same way (diagnoses, genetic results, medicines, findings, sex), so a researcher can judge similarity blind. Hidden values leave a visible placeholder ("2 hidden from view"), because scores and coverage still include them. Letters are masked only where a mention was annotated; unannotated text, such as a gene name in "panel sent (SCN1A)", can still show.
- **Terminology.** Diagnoses match through any coding of the concept or a narrower one. A broader code (ICD-10 G40.4 for Dravet syndrome) does not count unless a letter refines it, and the criteria panel says which codes count.
- **Free text.** Stated findings, optionally hedged findings; never negated, hypothetical or family-history mentions. A hedged diagnosis written before anything was coded is kept as its own earlier assertion.
- **Pairwise evidence.** For each feature the drawer splits values into *shared exactly*, *only in the reference* and *only in the match*, marking related-but-different values with ≈ (broader, narrower, same drug class). Hovering an event on either timeline gives the same verdict for that event and highlights its counterpart on the other timeline; hovering a value in the table highlights the events behind it.
- **Synthetic truth lens.** Shows what happened, including events never recorded and events after last contact, so the interface can be judged against a known answer.

## Define a trajectory

`trajectory/` is a cohort question with no reference patient, kept apart from the record view. It is defined in order:

1. **Index period.** The same two-ended window as the record view, placed per patient. It anchors the trajectory: every step can be required to fall anywhere, from its start onward, inside it, or after it ends, and constraints can start from its start or end.
2. **Trajectory.** Each step is an event found by searching name or code in any terminology the table holds (ICD-10, ICD-10-CM, SNOMED CT, ORPHA, OMIM, HPO, ATC, LOINC, HGNC, local); the concept also matches its narrower concepts through every coding, and its kind decides the condition. A finding or diagnosis is any occurrence, the first, the last recorded, the Nth, the Nth from last, or *at least N times* within a span or within the index period (the step then happens when the count is reached). A medicine or class takes the same choice of start. The index period's event takes first, last, Nth or Nth from last too. Occurrences are counted over reconciled events across the whole record, so a seizure entered by two sources counts once; "last" means last recorded and moves as follow-up grows, and among candidates it counts back from the latest possible start (D30). A gene is the first report that is not negative. A measurement (the seizure diary's monthly count, weight, height, head circumference) is a condition on the series: rises or falls by a factor against the mean of the one or two measurements before, or crosses a threshold. Timing constraints between steps are *starts between X and Y after* or *happens while taking*, optionally up to some time after stopping, each in its own unit. The page detects the shape and says what it means: a **sequence** (each step has at most one before and one after), a **tree** (branches from one root with no order between branches), or a **graph** (a step after several others). Cycles, dangling references and "while taking" on something that is not a medicine are rejected with a plain message. Sequence, Tree and Graph templates load worked examples.
3. **Matching patients.** Every patient is searched. Each step is bound to one of the patient's events, and the constraints are solved jointly as a simple temporal network: a step's time is its event's time, bounded by the event's recorded range, a medicine also has an end, and constraints bound the differences. Steps bound to the same event share its time, so one seizure cannot stand in for two seizures a month apart. A binding is *possible* if some choice of times inside the recorded ranges satisfies every constraint at once, which is checked exactly with shortest paths, and *exact* if every choice does. Results are exact, possible, relaxed with a declared cost (a broader concept, one fewer occurrence, the same drug class, a smaller change or a looser threshold, or a 1.5× longer gap), no recorded match, not comparable (the measurable steps match but the measurements cannot answer the rest), or no index period. Result types can be shown together; *no recorded match* and *no index period* are hidden until chosen, and *no recorded match* is then shown on its own. The detail drawer tags each bound step on the patient's timeline and gives a verdict for each constraint.

### Shortcuts these mockups take

- **Records are grouped into events by a stated rule that reads no generator truth** (`reconcile_v1`, `reconcile` in `shared/core.js`). It was introduced for index periods in D46, and since D47 builds the whole view: the page's own search (its fallback, and options the store does not answer, such as hedged findings), its timeline, its inspector and the patient-first page. The rule:
  - coded records of compatible concepts whose times meet are one event, most precise first;
  - an uncoded seizure-diary entry joins a seizure it meets;
  - medication courses follow the page's run-out rule (last dispensing, plus its supply, plus 45 days);
  - genetic records are grouped by gene;
  - letter mentions (stated or hedged, about the patient) attach by concept and the time their wording gives, or else form events of their own;
  - a hedged mention written before its event's first coded record stands as a separate, provisional event (on generator data this never fires: such a mention does not meet the later record, so it is its own event anyway).

  Events are then timed and named as before. A real system would have to infer the grouping in some such way, and could get it wrong; the rule can merge or split differently from what happened, and the inspector says so on every event. An independent reference (`index_reference.py`) checks every event and every index period. Records the rule cannot place are listed, with their data-quality cases, as "records the grouping rule could not place", not dropped. Examples are a record coded only in a local code no concept carries, or a diary entry that meets no seizure; no comparison reads them. Only the truth lens's display code reads the generator's truth: to show what happened, and which recorded events hold each true event. Two limits:
  - **No extraction step exists.** The generator writes each mention's span, concept, assertion, experiencer and time expression as it writes the letter, so findings in letters are perfect (misspelt, Dutch and French, hedged and negated mentions included), which flatters what letters add.
  - **Index periods are sent as exact times**, though the event that places one may be known only within a range (a day, a month, "about 3 weeks ago"). The store's answer holds for the period sent, not for every period the records allow (D46's P2; the next step is to make the anchor a step of the store's query, queued in D46).

  The store's matching reads none of this (`patterns/synthetic_ingest.py`).
- Data-quality cases are known because they were injected. With real data they would be detections, and some would be missed. Since D47 each attaches to the events, series readings, letters and unplaced records holding its records, never through its link to a true event.
- Event frequency counts recorded events, which are only the notable ones (an ED visit, a letter). Day-to-day frequency is in the diary's monthly counts, a measurement, so "4 seizures in a month" is a measurement condition here, not an event count. A real system would need both and would have to say which it used.
- SNOMED CT codes were added for a handful of concepts to make search across terminologies concrete. Like every code here they are illustrative and unverified.
- Trajectory search is backtracking with a budget of 40,000 attempts per search. A patient whose unrelaxed search exhausts it without a binding is *Unresolved*, shown by default, not a non-match; a found binding or a non-match that a stopped search leaves open carries a note saying what may have been missed. Relaxations are tried one or two at a time within a total cost of 1, and "exact" checks each constraint against the recorded ranges, each medicine's end being at or after its start, and the shared time of an event bound to two steps. Absence ("no X between A and B") and alternatives ("A or B") are not yet expressible.
- Similarity weights are equal and the distance rules are simple. They are placeholders for design discussion, not a proposal. Clinical findings and medication exposures can be compared by simGIC (the default), ancestor-Jaccard or best-match Resnik, as in the workspace engine. Information content comes from every patient's whole record in the 48-patient synthetic cohort, not from a searched database, and does not change with the window.
- The store query page uses the open MIMIC-IV demo, not synthetic data. It needs a store built locally and shows aggregate counts only.
- With the trajectory page on the store (D37), the answer shown is the store's, over every record and letter mention as recorded; the shortcuts above (records grouped by the page's rule, timed mentions, inferred courses) apply to the page's own search, to its fallback and to the index periods it places and sends.
- Layout is three columns at 1280 px and wider, stacked below. The narrow-screen tab layout, measured accessibility checks and browser testing beyond Chromium are not done.

## Datasets and access (D50)

`server.py` serves its stores as datasets from a registry (`datasets.py`), each with an access policy and a rule on
what it may return. The hosting design is in [docs/hosting-plan.md](../../docs/hosting-plan.md).

| Tier | Who may use it | Answers | Dataset |
|---|---|---|---|
| public | anyone, no sign-in | per patient (synthetic data only) | `synthetic-paediatric-rare`, the trajectory page's cohort |
| approved | signed in to the realm, and approved by the owner (group `approved`) | aggregate counts only | `mimic-iv-demo`, the store query page, when a store is configured |
| role | approved, and holding a role such as `dataset:mimic-iv:read`, granted after the owner checks and records the user's own PhysioNet credentialing | per patient | full MIMIC-IV: **refused by the server** until a storage and backup access review |

- **Floors.** Each kind of dataset has a minimum policy a registry cannot lower: the MIMIC-IV demo can never be
  public, and full MIMIC-IV (`kind: mimic-iv`) is refused outright for now. A registry may raise a policy. The
  `results` field must match what the backend produces. The content gates are unchanged: the MIMIC endpoints serve
  only the open demo's 100 patients, and the trajectory store only the generator's cohort. Counts-only is still not
  disclosure control (above).
- **Who is calling** (`access.py`). With `PTM_OIDC_ISSUER`, `PTM_OIDC_JWKS_URI` and `PTM_OIDC_AUDIENCE` set, an
  `Authorization: Bearer` access token from the realm, checked locally against the realm's public keys: RS256 only,
  issuer, audience, expiry, `sub`, `azp` (the configured client) and `typ: Bearer`. Roles come from
  `realm_access.roles`. A present but invalid token gets `401 TOKEN_INVALID`. A dataset the caller may not use is a
  `404 DATASET_NOT_FOUND`, like one that does not exist, and the old routes answer as if no such store were
  configured; the page reads why from `/api/datasets`. The keys come from `PTM_OIDC_JWKS_URI`, which is configured
  separately from the issuer (in-cluster on ids3); keys not refreshed for an hour are dropped.
- **Local use is unchanged.** With no realm configured and the server on a loopback address, the person at the
  machine is the owner and is served every configured dataset: `--mimic-store` works as before. Only a request
  addressed to `localhost`, `127.0.0.1` or `[::1]` is the owner, so DNS rebinding or a tunnel to the port gets
  public datasets only. On any other address, a non-public dataset without a realm means the server refuses to start.
- **Hosted** (any non-loopback bind): the anonymous engine route is off (the page uses the store, and falls back to
  the browser if the engine is chosen), only page asset types are served with no directory listings, and MIMIC
  stores open at startup. Synthetic-store matches run in a child process (`match_worker.py`, with a spare kept built) killed after
  `PTM_MATCH_TIME_LIMIT` seconds (default 2, at most 30; `503 MATCH_TIME_LIMIT`; a crash is `503 MATCH_WORKER_FAILED`;
  each kill is logged as `match_killed`), a match waits at most 3 s in all before `503 BUSY`, searches are clamped to 1,000 attempts per
  patient (a search that reaches it is `unresolved`, `SEARCH_BUDGET_EXHAUSTED`), and requests are capped at 6 steps, 8
  relations, 6 relaxations and a relaxation cost budget of 1. `GET /api/limits` says so, and the trajectory page shows
  it. The page's own requests never reach these bounds (D50). A realm needs `PTM_OIDC_CLIENT_ID` when hosted.
- **Endpoints.** `GET /api/datasets` lists the datasets the caller may use, and whether they are signed in and
  approved. `GET /api/auth-config` tells the page how to sign in. `/api/datasets/<id>/status`, `.../catalogue`
  (aggregate kinds only) and `.../match` address each dataset; `/api/trajectory-store/*` and `/api/store/*` stay as
  aliases of the first dataset of each kind the caller may use. `GET /api/ready` answers `{"ready": ...}`, 200 once
  every started dataset is ready (counts for the owner only; it never opens a store); `/api/health` answers from the
  start. `--datasets FILE` (or `PTM_DATASETS`) names a registry; without one the flags build it.
- **Limits and logs.** `PTM_MAX_BODY` (default 20 MiB), `PTM_MATCH_CONCURRENCY` (default unlimited locally, 4
  hosted; the slot is taken before a body is read; extra matches wait 3 s in all, then get `503 BUSY`), `PTM_MAX_THREADS`
  (requests in flight, default 64; beyond, 4 reserve threads serve only the probes, then `503 BUSY` at once), a
  30 s socket timeout, a 404 for any path holding a NUL byte, and caps on steps (12),
  relations and relaxations (40 each), and the engine route's patients (500) and events (50,000). With `PTM_LOG_FORMAT=json`, one JSON line per API request: route, status, duration,
  dataset, kind of caller and the token's subject; never a body, a token, a header or an address. Every response
  carries a Content-Security-Policy (scripts from this origin plus the hashes of the pages' inline scripts, computed
  at startup; `connect-src` self and the realm), `X-Content-Type-Options`, `Referrer-Policy` and `X-Frame-Options`,
  and a `Server` header without versions.
- **Sign-in on the pages** (`shared/auth.js`): PKCE against the realm's public client, with no library vendored. The
  access token is kept in memory, the refresh token in the tab's `sessionStorage` (the realm rotates it), so the next
  page gets a new access token without signing in again. Sign-out revokes the refresh token and ends the realm
  session. The index lists only the datasets the caller may use, and says when an account
  awaits approval. Without a realm none of this appears.
- **Dependencies.** The token check needs `requirements-hosting.lock.txt` (the store lock plus PyJWT and
  cryptography); it is imported only when a realm is configured.
- **Tests.** `test_access.py` covers the token check against keys generated in the test: expired, wrong-issuer,
  wrong-audience, tampered, re-signed, `none`/HS256/RS512 tokens, ID tokens, key rotation and an unreachable realm,
  plus each tier for each kind of caller. `test_datasets.py` covers the registry rules. `test_server_access.py` runs
  the server against a realm whose keys are served on loopback by the test: an anonymous caller reaches only public
  datasets, each token reaches its tier, bad tokens are refused everywhere, the log holds no token. It also covers
  local use, the non-loopback refusal, health during the build, and the body and concurrency limits, plus the
  security review's findings: the flood scaled down (bodies read only inside a match slot), the caps, the thread
  cap, the hosted surface, a malformed request line, the owner's Host check, readiness that opens nothing, and the
  Content-Security-Policy against every page. `test_auth_page.cjs` runs the sign-in and sign-out in Node. None needs

The target is the ids3 cluster, at `ptm.k8s.semanticscience.org`, with the synthetic cohort only on dev
([docs/hosting-plan.md](../../docs/hosting-plan.md); the draft manifests are in
[`deploy/ids3/ptm/dev/`](../../deploy/ids3/ptm/dev/)). Nothing is deployed yet.

The `Dockerfile` here serves the pages with nginx and regenerates the dataset during the build, so the generated
file is never uploaded. It has no server, so the store, the engine endpoint and the dataset endpoints are absent; the
pages fall back to the browser. No hosted copy of it is running; the Cloud Run service `ptm-mockups` was removed on
4 November 2026.
