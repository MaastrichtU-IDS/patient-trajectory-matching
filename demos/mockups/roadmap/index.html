Trajectory matching engine

A trajectory is steps plus timing constraints, as a sequence, a tree or a graph. Every patient gets a result, and the kinds stay apart: exact, possible, relaxed, unresolved, none and not comparable. Relaxations are priced within budgets, each event has one time, and an event can be marked as ending strictly after it starts. "First" and "last" are sound when the records leave their order uncertain: decided on the times the true first (or last) can take where that is exact, unresolved otherwise, and checked against every choice of times on small cases.

SULO source adapter

Turns bounded, patient-local and claim sources into the engine's input and checks every answer against the source's own time network. Shared source times are kept exactly. What it cannot represent it refuses, rather than guessing.

Execution store

DuckDB writing immutable Parquet snapshots. A snapshot is identified by a digest of its rows, and every build is verified by content. Patients stream in, so memory stays bounded. Candidates are pruned on stored time summaries before events are loaded, and matching runs in parallel worker processes, in Python.

MIMIC-IV demo pipeline

The open demo's input events go through the full graph route. Chart events are built in bulk from the importer's claim identity, with every row and every store also checked on the demo. Rows that cannot be admitted are kept as excluded records, so the store says not comparable rather than a false none. Committed reports carry aggregate counts only.

Queries on measurement values

A step can carry a condition such as "heart rate above 120 per minute" or "MAP below 65 mmHg", matched exactly on the stored values with the unit matched literally. Relaxing a threshold only ever adds patients, and excluded rows of the same item make a result not comparable. The matching engine itself is unchanged; the store compiles each condition into a tag for that query.

Store query page (stage 1 of the mockups on the store)

A mockup page builds trajectories on the MIMIC-IV demo's item classes, with value conditions and relaxations, and runs them in the execution store on the server. The server sends back aggregate counts only and refuses any snapshot that is not the open demo; tests check both. The server checks that the store holds the open demo's own patients, not just its label. Counts alone are not disclosure control, so it serves only the open demo. On the synthetic cohort, the store and the trajectory page agree on 401 of 480 patient results; each of the other 79 has a named cause (letter mentions, merged records, medication courses, uncertain first or last targets, and the store's coverage rule).

The store under the trajectory page (stage 2)

The trajectory page matches in the store by default once the store can express everything the page offers, or refuses it by name, and the parity test is clean, with every difference removed or declared and the converter itself emitting measurement values. The store needs Nth occurrences; "at least N times within" a span; rises and falls against earlier values (a design decision first); gene results that are not negative; free text as a query option; and index periods placed by rule. Each record-level difference (merged records, letter mentions, medication courses, coverage) moves into the converters or is declared. The browser path stays as a fallback for static hosting. Stage 3, retiring it, waits for the hosting decision.

D27 stage 3

Selection "as known at" a date

Records carry when they became available, but selection uses the latest version today. Applying availability would let a study see only what was known at its index date. The typed record fields of store 3.0 are what this needs.

D26 · docs/execution-store.md, "Deliberately not done"

Incremental appends

Adding patients without rebuilding the whole store: per-bucket digests, so an append rehashes only what it touches, with a per-patient (Merkle) input digest wired in at that point.

The exclusion rule reads only a query's scope. Reading its anchor relations too would turn fewer results incomparable, once differential tests cover it.

A Rust matching engine

Built only if Python misses the latency target and algorithmic work cannot recover it. Python met the target at 300,000 patients until D30; with sound first and last and wider letter mentions it is now missed (p95 13.05 s against 10 s at 14 workers), so D21's rule applies again, algorithmic work first. A Rust engine would be a second implementation over the same snapshots, with the Python path as its reference.
