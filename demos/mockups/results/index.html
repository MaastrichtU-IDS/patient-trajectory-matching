Execution store and matching: what the evidence shows

Every figure on this page is read from a committed verification report, listed at the bottom with its digest. Scale figures use synthetic patients on one machine; beyond 10,000 patients the cohort replicates a pool of 10,000 distinct patients. The MIMIC-IV figures use the open demo (100 patients) and show aggregate counts only. Nothing here is a clinical claim.

Matching speed at 300,000 patients

Full-detail match() over queries, each repeated times, with the engine's work spread over worker processes. The target, fixed before measuring (D21): 95th-percentile latency at most s, slowest query at most s, and query-process memory under GiB. Because it is met in Python, no Rust engine was built.

Building and verifying the store as the cohort grows

DuckDB writes immutable Parquet snapshots under a memory limit with one database thread. Each snapshot is identified by a digest of its canonical rows, and every build is verified by content. Single-process match times are over the main run's queries at each size (50 at 1,000 and 10,000; 10 above).

Build peak is the whole process's resident memory, about twice DuckDB's limit; the factor is unresolved (DuckDB or the allocator). The 1,000,000 snapshot is shaped by replication of the 10,000-patient pool, so its size is not a linear extrapolation.

MIMIC-IV demo: inputevents and chartevents in one store

The open MIMIC-IV demo, fetched locally and checksum-verified, never committed. Input events go through the full graph route; chart events are built in bulk from the importer's claim identity (route b), and on the demo every row and every store was also checked, not a sample.

The raw-row check recomputes every chart row from the source file with code independent of the converter. The graph route shares code with the bulk route, so on its own it checks the claim's round trip and acceptance, not the shared conversion.

Most results are not comparable: only numeric chart rows with a unit are admitted, and an excluded row of the same item might have changed the answer, so the store does not claim none there (D18).

Limits of this evidence

  • One machine (), one DuckDB thread, one memory limit.
  • Synthetic data, replicated beyond 10,000 patients: candidate counts and outcomes multiply exactly, and a million distinct patients was never built.
  • Latency at 100,000 patients and above in the main runs rests on ten queries; the target is judged on the 30-query, 3-repeat confirmation.
  • Run-to-run spread between benchmark runs is not fully explained; the decision log records each instance.
  • Parallel matching at 1,000,000 patients was not measured.
  • The MIMIC store indexes source item classes, not reviewed clinical concepts.
